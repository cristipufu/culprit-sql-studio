missing-index     Missing indexes
                  SQL Server · Index suggestions recorded by SQL Server's optimizer, merged with each other and checked against existing indexes.
filtered-scan     Scans an index would avoid
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Heavy queries whose plan reads a large table in full and keeps only the rows matching a filter that no index supports.
unused-index      Unused indexes
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Indexes that are maintained on every write but no query has read since usage counters were reset. One that may be less than a week old (a scan saw it appear, or its table changed before Culprit's first scan) isn't called unused yet.
duplicate-index   Duplicate and redundant indexes
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Indexes with the same keys as another index, or whose keys are a leading part of a wider one.
unindexed-fk      Foreign keys without an index
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Foreign key columns with no index starting with them, which makes deletes on the parent and joins from the child slow.
overlapping-index  Overlapping indexes
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Two indexes that lead with the same column where one is barely read and the other holds all its key columns: queries that use the first can seek the second and filter the rest there.
over-indexed      Many indexes on write-heavy tables
                  SQL Server, PostgreSQL, MySQL/MariaDB · Tables with many secondary indexes that are written a lot: every insert updates each index.
scan-heavy        Tables read in full over and over
                  PostgreSQL, MySQL/MariaDB · Large tables that queries read in full many times a day, from the table scan counters.
tuning-advice     SQL Server's own tuning advice
                  SQL Server · Plan-forcing and index recommendations from automatic tuning, forced plans (those that stopped applying, and those that scan where an index added since could seek), Query Store hints that stopped applying, and automatic plan correction left off.
query-family      Statements with literals baked in
                  SQL Server, PostgreSQL, YugabyteDB · The same statement sent many times with different literal values (or value-list lengths), so the database compiles and tracks each copy separately; and plan caches filled with single-use plans.
logged-errors     SQL errors recorded by the application
                  SQLite · Recognized error codes in structured query logs, including errors with no duration. Counts describe log records, not failed business requests or zero-cost executions.
repeated-request  Repeated statements within logged requests
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Repeated SQL shapes correlated by explicit request_id in structured logs. Repetition identifies a caller to inspect; it does not prove an N+1 bug or removable work.
heavy-query       Queries that dominate database time
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Single queries that take a large share of database time, with what their plan spends it on.
chatty-query      Chatty queries
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Tiny queries executed so often that the round trips cost more than the work, typically a loop in application code.
plan-warnings     Plan warnings
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Implicit conversions, spills, missing join predicates and missing statistics in the plans of heavy queries.
plan-insights     Plan insights
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Key lookups, functions on filtered columns, leading wildcards, NOT IN, scalar functions, eager spools, misestimates and repeated loops in the plans of queries that matter.
plan-regression   Plan regressions
                  SQL Server · Queries whose current plan is much slower than a plan they used before.
regression        Queries that got slower
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Queries whose runs became much slower at some point in the window, with when it started and whether a plan change coincides. Needs Query Store history or a few earlier scans.
unstable-query    Unstable queries
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Queries whose duration swings wildly between runs with the same plan, a sign of parameter sensitivity or blocking.
parameter-sensitive  Queries that are fast for most calls and slow for some
                  SQL Server, MySQL/MariaDB · Statements whose run time depends heavily on the values they run with: two plans used side by side, one fast and one slow (SQL Server Query Store), or a long tail in the run-time histogram (MySQL). Single-plan variance on any engine is `unstable-query`.
temp-spill        Queries writing temp files
                  PostgreSQL, MySQL/MariaDB · Statements whose sorts, hashes or temporary tables outgrow memory and spill to disk.
stale-stats       Stale statistics
                  SQL Server, PostgreSQL · Tables whose optimizer statistics are far behind their data, which leads to bad row estimates and plans.
heap-table        Large tables without a clustered index
                  SQL Server · Heaps grow forwarded records and can't be read in key order; most OLTP tables should be clustered.
dead-rows         Dead rows and lagging autovacuum
                  PostgreSQL · Tables carrying many dead tuples, which bloat storage and slow scans.
xid-age           Transaction ID wraparound risk
                  PostgreSQL · Transaction ID age approaching the point where PostgreSQL stops accepting writes to protect data.
multixact-age     MultiXact wraparound risk
                  PostgreSQL · The independent PostgreSQL MultiXact age limit, which can reject row-locking writes even when ordinary transaction ID age is healthy.
config            Configuration
                  SQL Server, PostgreSQL, MySQL/MariaDB, SQLite · Database and server settings that commonly hurt performance or hide the data needed to diagnose it.
deadlocks         Deadlocks
                  SQL Server, PostgreSQL, MySQL/MariaDB · Deadlocks in the last day, grouped by pattern (key lookup, opposite order, read-then-update, lock escalation, parallelism) with the fix that removes them. SQL Server reads system_health, Azure SQL Database an explicitly configured database-scoped event session, MySQL the latest InnoDB report, and PostgreSQL only keeps a counter.
memory-grant      Queries that reserve far more memory than they use
                  SQL Server · Statements whose memory grant (reserved before they run, for sorts and hashes) is many times what they use, so other queries queue for memory.
memory-queue      Queries waiting in line for memory
                  SQL Server · Waiting for memory takes a real amount of time (a minute an hour or more), or queries in this database were queueing for a memory grant when the scan ran.
compile-pressure  Instance compilation context
                  SQL Server · Shared compilation counters provide context for this database's literal query families; measured Query Store costs establish its compilation impact.
compile-queue     Compiler admission
                  SQL Server · Requests in this database delayed by compiler admission, with recent per-query compile-memory evidence where available.
worker-pressure   Running out of workers or connections
                  SQL Server, PostgreSQL, MySQL/MariaDB · SQL Server sessions waiting for a worker thread (THREADPOOL), or PostgreSQL/MySQL connections close to max_connections.
held-cleanup      A long open transaction holds cleanup back
                  SQL Server, PostgreSQL, MySQL/MariaDB · The transaction that holds this database's cleanup back: one with uncommitted changes or row versions here (SQL Server), the oldest snapshot, replication slot or prepared transaction behind VACUUM's horizon (PostgreSQL), or the oldest read view behind InnoDB's purge (MySQL).
network-wait      Queries with recorded network waits
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Statements with material recorded network waits. These totals do not by themselves identify a slow client, transport problem or responsible component.
tier-limit        Resource use near the cloud tier's limits
                  SQL Server · Azure SQL Database resources (CPU, data IO, log writes, workers) persistently near their limits in the available selected-period samples.
checkpoint-pressure  Requested checkpoints
                  PostgreSQL · The server's requested checkpoints, with the possible causes and the evidence needed before changing WAL settings.
row-lock-waits    Transactions waiting for row locks
                  MySQL/MariaDB · InnoDB row-lock waits add up to real time (a minute an hour or more across the server), from long transactions or updates that scan instead of using an index.
storage-capacity  Files and logs near their allocation limits
                  SQL Server · Current database file and transaction-log capacity, log reuse reasons, and shared tempdb allocation. Autogrowth room is distinguished from a hard limit.
sequence-capacity  Identity and sequence allocation limits
                  SQL Server, PostgreSQL, MySQL/MariaDB · Non-cycling identities, sequences and auto-increment columns approaching their numeric bounds; cache allocation is not a forecast of remaining requests.
operational-errors  Archive, replication and redo failures
                  PostgreSQL, MySQL/MariaDB, SQL Server · WAL archive failures, logical subscription errors, standby recovery cancellations, InnoDB redo buffer waits, connection handshake failures, and storage page checksum or I/O corruption errors. Counter history is kept separate from newly observed errors.
cluster-health    Galera node readiness and flow control
                  MySQL/MariaDB · The current readiness, connectivity and primary-component verdict reported by a Galera node; its historical flow-control fraction is context, not database-specific pressure.
sqlite-wal        SQLite WAL file size and growth
                  SQLite · Read-only WAL sidecar metadata and changes between scans; retained allocation is not inferred to be a checkpoint backlog or a blocked reader.
failing-query     Queries that fail or time out
                  SQL Server, MySQL/MariaDB · Statements whose runs end in an error or are cancelled by the client (usually a command timeout): Query Store's aborted and exception runs, performance_schema's errors per digest. PostgreSQL keeps no per-statement error count.
planning-time     Queries that spend their time being planned
                  SQL Server, PostgreSQL · Statements where planning (PostgreSQL, with pg_stat_statements.track_planning on) or compiling (SQL Server Query Store) takes a large part of their time, usually because the plan isn't reused.
jit-overhead      JIT compilation that takes much of a statement's time
                  PostgreSQL · Statements where PostgreSQL's JIT compilation (pg_stat_statements jit_* columns, 15+) takes a large part of their run time.
log-volume        Writes that produce most of the log
                  SQL Server, PostgreSQL · Statements that write a large share of the WAL (PostgreSQL 13+) or transaction log (SQL Server 2017+), or many kilobytes of it per row changed. Log volume drives replication lag, backup size and checkpoints. MySQL keeps no redo bytes per statement.
lock-time         Queries with material recorded lock waits
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB, SQLite · Statements with material recorded lock waits. Totals can accumulate across workers and do not identify the lock resource or blocking request.
big-result        Queries that return huge results
                  SQL Server, PostgreSQL, YugabyteDB, MySQL/MariaDB · Reads that send tens of thousands of rows to the application on every run, with an estimate in bytes from the plan's row width where the engine gives one.
hot-rows          Rows that many sessions fight over
                  SQL Server · Indexes where sessions waited a long time for row and page locks, and where locks escalated to the whole table (sys.dm_db_index_operational_stats). MySQL, MariaDB and PostgreSQL keep no lock waits per table; see lock-time and Live.
lock-escalations  Statements that lock a whole table
                  SQL Server · Tables where one statement took so many row or page locks that SQL Server replaced them with a lock on the whole table (sys.dm_db_index_operational_stats). MySQL, MariaDB and PostgreSQL never escalate row locks.
last-page-insert  Index page-latch contention
                  SQL Server · Index-level in-memory page-latch waits, with possible causes separated from confirmed page and query evidence.
untrusted-constraint  Unvalidated or disabled constraints
                  SQL Server, PostgreSQL, YugabyteDB · SQL Server foreign keys and check constraints added or re-enabled WITH NOCHECK (or switched off), PostgreSQL CHECK constraints added NOT VALID, and YugabyteDB CHECK or foreign-key constraints awaiting validation.
missing-histogram  Filter columns the optimizer has to guess about
                  MySQL/MariaDB · Columns that heavy queries filter on with no index leading on them and no histogram (MySQL 8 COLUMN_STATISTICS, MariaDB mysql.column_stats), so the optimizer assumes a fixed share of rows match.
hot-updates       Updates that rewrite every index
                  PostgreSQL · Tables where few updates are HOT (heap-only): each other update writes a new entry in every index and leaves cleanup for VACUUM. Says whether pages are too full (fillfactor) or an indexed column changes (PostgreSQL 16+ tells them apart).
table-bloat       Tables that are mostly empty space
                  PostgreSQL · Tables whose pages hold far fewer rows than they could, estimated from row counts and column widths in pg_stats (no extension needed). Every scan still reads the empty space.
large-rows        Tables whose rows are mostly large values
                  SQL Server, PostgreSQL · Tables whose rows average many kilobytes, most of it in large values kept apart from the rows (SQL Server's LOB pages, PostgreSQL's TOAST): every statement that reads whole rows pulls them in, every write that sets them writes them again. From the catalog's page counts; no data is read.
slow-storage      Storage that's slow to read or write
                  SQL Server, PostgreSQL, MySQL/MariaDB · Average read and write latency per database file since startup: sys.dm_io_virtual_file_stats, pg_stat_io (16+, with track_io_timing), performance_schema file I/O.
connection-churn  Applications that connect for every request
                  SQL Server, PostgreSQL, MySQL/MariaDB · New connections per second since startup (SQL Server logins, PostgreSQL 14+ sessions, MySQL and MariaDB Connections), with how long sessions last and how many came from a pool where the engine says.
replica-lag       Replicas that fall behind
                  SQL Server, PostgreSQL, MySQL/MariaDB · Replicas far behind the primary or stopped, and PostgreSQL replication slots that keep WAL for a consumer that's gone: pg_stat_replication, availability group replica states, SHOW REPLICA STATUS.
last-actual-plans  Actual plans without re-running queries
                  SQL Server · SQL Server 2019+ can keep each query's last actual plan (LAST_QUERY_PLAN_STATS) and report live per-operator progress (LIGHTWEIGHT_QUERY_PROFILING).

1 deadlock (file).

2026-10-11 13:48:28 Two transactions locked customers in opposite order and waited on each other; session 539's transaction was rolled back.
  Each transaction had already changed rows the other one wanted next: session 539 was running “UPDATE customers SET id = id WHERE id = 1” and session 545 “UPDATE orders SET id = id WHERE id = 1”. With the same order in both, the second would simply wait instead of deadlocking.
  rolled back  session 539
               UPDATE customers SET id = id WHERE id = 1
               session 545
               UPDATE orders SET id = id WHERE id = 1
  1. Touch tables and rows in the same order everywhere: Make every code path that changes customers do it in one order (for example, always the parent row first, and rows sorted by key). Then the second transaction waits instead of deadlocking.
  2. Keep transactions short: Do reads, validation and outside calls before the transaction starts; hold locks only for the writes.
  3. Retry the victim: A deadlock victim can be retried safely; the application should catch SQLSTATE 40P01 and run the transaction again.
