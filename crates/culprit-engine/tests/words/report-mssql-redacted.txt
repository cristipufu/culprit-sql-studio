### A read from order\_items times out on every run, at about 15 s

**100% of runs fail** · Needs attention · high impact, high confidence · SQL Server 2022, local environment

The associated statements used 2 min of database time over the last 5 hours (27%). None of its 6 runs in the last 5 hours finished. 6 were cancelled by the client after 15.0 s on average, which is what a command timeout looks like. A run that doesn't finish still costs the time it ran, and the application retries it or shows an error.

- Runs: **6**
- Didn't finish: **100%**
- Cancelled: **6**
- Cancelled after: **15.0 s**

**Query `263`** · 27% of database time · 6 runs over the last 5 hours · 15.0 s on average

```sql
SELECT COUNT_BIG(*) FROM shop.order_items a JOIN shop.order_items b ON a.id % ? = b.id % ? OPTION (LOOP JOIN, MAXDOP 1)
```

**Fix.** Cancelled runs are almost always the application's command timeout (here about 15 s; 30 s is the default in ADO.NET and most drivers). Make the statement faster first: open its plan. If it legitimately runs long, raise the timeout for this call only.

**How to verify**

1. Re-scan after the change: runs that fail or are cancelled should drop to near zero.
2. After it ships: `culprit verify <connection> failing-query:263` re-scans and reports whether it's gone.

### A read from orders fails 25% of the time

**25% of runs fail** · Needs attention · high impact, high confidence · SQL Server 2022, local environment

The associated statements used 9.1 ms of database time over the last 5 hours (&lt;1%). 50 of its 200 runs in the last 5 hours didn't finish. 50 ended in an error. A run that doesn't finish still costs the time it ran, and the application retries it or shows an error.

- Runs: **200**
- Didn't finish: **25%**
- Errors: **50**

**Query `246`** · <1% of database time · 200 runs over the last 5 hours · 0.05 ms on average

```sql
SELECT TOP (?) total / @d AS share FROM shop.orders WHERE id = ?
```

**Fix.** Query Store counts the errors but doesn't keep them. Capture them for a while with an Extended Events session on error\_reported for this database, read the ring buffer, then drop the session.

```sql
-- Capture errors raised in this database (one session for every failing statement: once is enough)
IF NOT EXISTS (SELECT 1 FROM sys.server_event_sessions WHERE name = N'culprit_errors')
    CREATE EVENT SESSION culprit_errors ON SERVER
    ADD EVENT sqlserver.error_reported (
      ACTION (sqlserver.client_app_name, sqlserver.sql_text)
      WHERE severity >= 11 AND sqlserver.database_name = N'culprit_demo')
    ADD TARGET package0.ring_buffer;
IF NOT EXISTS (SELECT 1 FROM sys.dm_xe_sessions WHERE name = N'culprit_errors')
    ALTER EVENT SESSION culprit_errors ON SERVER STATE = START;
-- Once it has caught what you need, stop and remove it: DROP EVENT SESSION culprit_errors ON SERVER;
```

**How to verify**

1. Re-scan after the change: runs that fail or are cancelled should drop to near zero.
2. After it ships: `culprit verify <connection> failing-query:246` re-scans and reports whether it's gone.

### Queries on orders recorded lock waits in the last 5 hours

**3 min waiting on locks** · Needs attention · medium impact, high confidence · SQL Server 2022, local environment

The associated statements used 3 min of database time over the last 5 hours (56%). Since its index pk\_orders was loaded into memory, sessions waited 5 times for locks on the rows and pages of orders, 3 min 7 s in all, 37.3 s each on average. Waits like these come from transactions that hold rows for long, or from writes whose filter isn't indexed and so lock more rows than they change. No comparable earlier counters place these waits in the selected window or establish that contention continues. An update of orders waited 2 min for these locks in the last 5 hours, nearly all of its time. A read from orders waited 1 min for these locks in the last 5 hours, nearly all of its time.

- Historical lock waits: **5**
- Historical time waiting: **3 min**
- Historical average wait: **37.3 s**

**Query `138`** · 34% of database time · 4 runs over the last 5 hours · 28.7 s on average

```sql
UPDATE [shop].[orders] set [status] = [status]  WHERE [id]=@1
```

**Query `143`** · 21% of database time · 3 runs over the last 5 hours · 23.9 s on average

```sql
SELECT [status] FROM [shop].[orders] WHERE [id]=@1
```

**Query `161`** · <1% of database time · 4 runs over the last 5 hours · 601 ms on average

```sql
UPDATE [shop].[orders] set [total] = [total]+@1  WHERE [id]=@2
```

**Fix.** It ran 4 times in 5 hours, too seldom to count on catching it while it waits. Have the next ones reported instead: SQL Server's blocked process report names the session holding the lock, with its statement, for each wait longer than the server's blocked process threshold (s) (0, off, by default; sp\_configure sets it). Capture sqlserver.blocked\_process\_report in an event session to keep them. Keep the holding transactions short and commit before slow work; make UPDATE and DELETE filter on an index so they lock only the rows they change; touch rows in the same order everywhere. Query 143 recorded lock waits while READ\_COMMITTED\_SNAPSHOT is off. Row versioning is a candidate; confirm read-committed data-lock waits before changing isolation.

**How to verify**

1. Compare new lock waits and their time between scans under comparable load on orders. An unchanged counter reports no new waits; an idle interval alone does not verify a fix.

**Before you act**

- These counters cover each index metadata entry’s lifetime, which can end without a server restart.

### Compares each of 1.5M rows of order\_items with 999 rows the Table Spool replays (1.5B pairs)

**27% of DB time** · Needs attention · medium impact, medium confidence · SQL Server 2022, local environment

The associated statements used 2 min of database time over the last 5 hours (27%). The Table Spool reads order\_items once and replays its 999 rows for each row of order\_items; the join then checks \`Expr1003 = Expr1004\` on every pair. 100% of this plan's work. The query forces a loop join, so the optimizer didn't weigh a hash or merge join. Seen in a read from order\_items.

- Share of DB time: **27%**
- Share of the plan's work: **100%**
- Average duration: **15.0 s**

**Query `263`** · 27% of database time · 6 runs over the last 5 hours · 15.0 s on average

```sql
SELECT COUNT_BIG(*) FROM shop.order_items a JOIN shop.order_items b ON a.id % ? = b.id % ? OPTION (LOOP JOIN, MAXDOP 1)
```

Plan: the step to look at is **Nested Loops** (94% of the plan's cost, 1.5M rows, on `Expr1003 = Expr1004`).

**Fix.** The query forces a loop join (LOOP JOIN / OPTION (LOOP JOIN)); remove the hint and let the optimizer choose.

**How to verify**

1. Explain again without the hint: a hash or merge join instead of the loop.
2. Re-scan: this finding is gone.
3. After it ships: `culprit verify <connection> plan-insights:nested-loops:query-263` re-scans and reports whether it's gone.

**Before you act**

- Based on the estimated plan; actual row counts can tell a different story.
