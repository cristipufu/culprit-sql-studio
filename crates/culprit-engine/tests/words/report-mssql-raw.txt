### Row locks on support\_tickets escalated to a table lock 5 times since SQL Server started (Oct 11)

**5 table locks** · Needs attention · high impact, high confidence · SQL Server 2022, local environment

SQL Server replaced the row and page locks on support\_tickets with one lock on the whole table 5 times since it started, on Oct 11 at 11:06 UTC, 67 minutes before this scan, so none is older than that. The next scan compares with this one and says whether any happened since. That is once a day or more on average over the counter history; it does not date individual events. SQL Server can attempt escalation around 5,000 locks on one table reference, or under lock-memory pressure. A successful table lock can block incompatible lock requests until the transaction ends; the escalation counter alone does not establish that other sessions were blocked. SQL Server doesn't record which statement it was, and none of the statements in the query history writes to support\_tickets. A read can escalate too: an ordinary read under read committed usually releases row locks as it advances, but prefetching key lookups can retain locks until the statement ends. Locking hints (HOLDLOCK, UPDLOCK), REPEATABLE READ and SERIALIZABLE can retain them until the transaction ends. Reading many rows can acquire enough locks for an escalation attempt. The likeliest is a read from support\_tickets, which returns about 973 rows a run on average: its plan prefetches its key lookups, which keeps their row locks until the statement ends.

- Escalations since SQL Server started: **5**

**Query `10`** · 2% of database time · 4.0K runs over the last 5 hours · 1.4 ms on average

```sql
SELECT [id], [subject], [opened_at], [status] FROM [shop].[support_tickets] WHERE [priority] = @P1
```

**Fix.** Start the event session below (culprit\_lock\_escalation) to learn which statement escalates: it keeps each escalation with its statement, in memory, at almost no cost. If it is a read, it escalates because it keeps its row locks until it ends: Without locking hints, READ\_COMMITTED\_SNAPSHOT lets ordinary reads under read committed avoid row locks (it changes what readers see and uses tempdb, so test it first); or consider reading fewer rows per run after checking the access path; row counts do not bound all locks or prevent escalation under lock-memory pressure. If it is a statement outside the query history that changes many rows at once (a job, a migration, maintenance), consider smaller batches. Use separate transactions only if partial commits preserve required atomicity; an enclosing transaction may retain locks.

### Inserts into hot queue for the last page of pk\_hot

**53.6 s latch waits** · Needs attention · high impact, medium confidence · SQL Server 2022, local environment

pk\_hot starts with a value that only grows (id), so every insert goes to the same last page. Concurrent inserts wait for each other's latch on it (PAGELATCH\_EX): 106K waits, 53.6 s in all since the index was loaded. It gets worse with more concurrent writers.

- Page latch waits: **106K**
- Time waiting: **53.6 s**
- Inserts: **128K**

**Fix.** SQL Server 2019 can pace concurrent inserts into a sequential key to help sustain throughput when many writers compete for the last page: try OPTIMIZE\_FOR\_SEQUENTIAL\_KEY on this index and compare throughput. It's a metadata change and takes effect at once.

```sql
ALTER INDEX [pk_hot] ON [archive].[hot] SET (OPTIMIZE_FOR_SEQUENTIAL_KEY = ON);
```

**How to verify**

1. Re-scan to confirm OPTIMIZE_FOR_SEQUENTIAL_KEY is ON. Compare completed inserts per second and the time to insert the same batch before and after, under comparable writer concurrency: the goal is better insert throughput under contention.
2. Page-latch waits can continue, and BTREE_INSERT_FLOW_CONTROL waits may appear. Compare measurements over equal intervals; cumulative wait totals need not stop growing.
3. After it ships: `culprit verify <connection> last-page-insert:archive.hot.pk_hot` re-scans and reports whether it's gone.
