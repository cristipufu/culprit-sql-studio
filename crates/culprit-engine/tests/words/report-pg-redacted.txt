### A read from orders writes about 19.9 MB of temp files per run

**44% of DB time** · Needs attention · medium impact, high confidence · PostgreSQL 18.6, local environment

The associated statements used 1 min of database time over the 5 hours since statistics were reset (44%). A sort or hash in this statement needs more memory than work\_mem (4MB in Culprit's session; a setting on the application's role or database can differ) and writes the overflow to temporary files: 4.2 GB over 214 runs. pg\_stat\_statements counts the total, so whether every run spills or only some is unknown. Writing temp files and reading them back is many times slower than sorting in memory. Each run also sends 247K rows (≈ 17.4 MB) to the application, and few screens or jobs need that many at once: returning fewer can keep the sort in memory too. Latest activity: 25 runs observed over 32 minutes of Culprit's scans on Oct 11, 11:22–11:54 UTC. This count is shown without extrapolating a daily rate.

- Temp written per run: **19.9 MB**
- Average duration: **332 ms**
- Rows per run: **247K**
- Bytes per run (estimated): **17.4 MB**

**Query `9065391607317686058`** · 44% of database time · 25 runs observed over 32 minutes of Culprit's scans on Oct 11, 11:22–11:54 UTC · 332 ms on average

```sql
SELECT id, note FROM orders WHERE created_at > now() - interval $1 ORDER BY note
```

Plan: the step to look at is **Sort** (667K rows). The rows it works on rest on the planner's default guess for a parameter, not on the table's statistics, so no share is given.

**Fix.** Give this statement more sort memory (64MB instead of 4MB, if the application's role doesn't already set more), for the role the application connects as or only around this statement, rather than server-wide; or add an index that returns rows already in the order the sort needs, or sort fewer rows. Where the application doesn't use every row it receives, return only what's used: page the results (keyset pagination, or LIMIT / OFFSET … FETCH), filter in SQL rather than in the application, select only the columns you need, and aggregate in the database.

```sql
-- For the role the application connects as (takes effect on its next connections):
ALTER ROLE <app_role> SET work_mem = '64MB';

-- Or only for this statement, inside its transaction:
SET LOCAL work_mem = '64MB';
```

_Cost:_ work\_mem is per sort or hash, per connection: size it with your connection count in mind.

**How to verify**

1. Once the application's connections use the new setting (a role's setting reaches the connections it opens after the change), its temp files should stop growing while its runs go on: pg_stat_statements keeps running totals, so compare its temp files and runs in a scan taken once the change is live and one a day or more later (4.2 GB over 214 runs in this scan).
2. If it now returns fewer rows, the rows it returns per run between those two scans should drop to what a page or a job actually uses.

### The inactive replication slot analytics\_slot keeps 1.1 GB of WAL

**1.1 GB of WAL kept** · Needs attention · medium impact, high confidence · PostgreSQL 18.6, local environment

A replication slot keeps every WAL file its consumer hasn't confirmed. analytics\_slot has no consumer connected, so the WAL it holds keeps growing. It is a physical slot: a standby or a backup tool streams WAL through it. Unless max\_slot\_wal\_keep\_size caps what slots keep, it grows until the disk fills and the server stops accepting writes.

- WAL kept: **1.1 GB**

**Fix.** If nothing will stream through this slot again (a standby that was removed), drop it. If max\_slot\_wal\_keep\_size isn't set, cap what slots may keep so none can fill the disk: Set max\_slot\_wal\_keep\_size to 50GB and reload the configuration (settings marked as needing a restart take effect after one).

```sql
SELECT pg_drop_replication_slot('analytics_slot');
-- If max_slot_wal_keep_size isn't set, cap what any slot may keep:
ALTER SYSTEM SET max_slot_wal_keep_size = '50GB';
SELECT pg_reload_conf();
```

**How to verify**

1. Re-scan: the slot should be gone, or active again.
2. After it ships: `culprit verify <connection> replica-lag:analytics_slot` re-scans and reports whether it's gone.

**0% HOT** · Optional improvement · low impact, high confidence · PostgreSQL 18.6, local environment

The associated statements used 327 ms of database time over the 5 hours since statistics were reset (&lt;1%). An update that changes no indexed column and finds room on the same page is HOT: it writes no index entries and its old version is cleaned up without VACUUM. - Updates: **21K**
- HOT: **0%**

- Fillfactor: **100**

**Query `-463560455567765064`** · <1% of database time · 1 run over the 5 hours since statistics were reset · took 327 ms

```sql
UPDATE archive.wide SET touched = touched + $1 WHERE id % $2 = $3
```

**Fix.** Leave room on each page so updated rows fit next to the old version: a fillfactor of 85–90 is typical for tables updated often. It applies to pages written from now on; existing pages get the room as rows move (pg\_repack rewrites the table online if you want it at once). If an index covers a column that changes on every update (updated\_at, status, counters), dropping it makes those updates HOT too.

```sql
ALTER TABLE archive.wide SET (fillfactor = 85);
```

**How to verify**

1. Re-scan a few days later: the HOT share counts since the last statistics reset, so compare how n_tup_hot_upd grows against n_tup_upd.
2. After it ships: `culprit verify <connection> hot-updates:archive.wide` re-scans and reports whether it's gone.

**Before you act**

- The update behind most of these ran once in the 5 hours since statistics were reset: a backfill or a migration looks like this, and its share stays in the counts long after. It needs work only if updates like it keep coming.
- How long these counts have run isn't known (PostgreSQL 15+ records no start until its statistics are first reset, and the counts outlive restarts): one large update or backfill long ago would keep the share low. Compare how n_tup_hot_upd grows against n_tup_upd over a few days before changing the table.
